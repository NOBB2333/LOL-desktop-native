## 1. 初始完成度判断

本节及后面的原始问题列表保留第一次评估时的判断，用于追溯改造原因；当前完成情况以顶部实施更新为准。

目前是“主要流程已搭建、具备真实使用基础，但还需要补齐可靠性和体验”的版本。按本项目自己的桌面辅助目标，功能骨架约七到八成，稳定使用闭环约六成。这是依据下列功能矩阵作出的工程估算，不是测试覆盖率，也不是 LeagueAkari 全量功能的移植比例。

值得保留的是 Native SDK + Zig + Vue 的方向。LCU 凭据、网络访问、输入模拟留在原生层，Vue 负责呈现；已有账号隔离、跨阶段阵容保留、快速阵容、缓存、自动化防重复和组件测试。没有必要为了追平 Akari 的体验更换 Electron 或重新搭建整套应用。

优先级应是：加载可靠性和“遇到过”的完整体验，随后是数据真实性、失败恢复和实机验收。AI、更多独立窗口、复杂阵容算法可以后排。

## 2. 关键发现

### R1 / P1：异步 bridge 仍由一个 worker 串行执行

`src/main.zig:217` 的 worker 每次取一个任务，直接调用 `processAsyncBridgeJob`；`src/main.zig:255` 又在绝大多数 handler 的整个执行期间持有 `command_mutex`。

结果是：`get_live_lobby` 等待玩家网络查询时，后来的 `get_live_roster`、资源图标、历史、事件和快捷消息都要排队。前端 `frontend/src/services/native.ts:17` 的并发数 4 只是允许四个未完成的调用，并不代表后台有四个并行 handler。

`src/backend.zig:225` 的自动化 watchdog 在复制配置前也要获取这把锁，且 `src/backend.zig:339` 是自旋等待。独立线程并没有完全隔离开长查询的影响。

改造应缩小锁范围、给快速状态和交互命令保留通道，并将玩家资料加载变成后台任务。不能直接删除锁，Runtime 里仍有共享缓冲区和可变状态。

### R2 / P1：第一次信息没拉全，后续刷新可能一直复用缺失结果

`src/backend.zig:714` 在 roster hash 相同、`live_lobby_enriched` 为 true 时直接返回缓存。`src/backend.zig:730` 却将该标记赋为“本次请求要求 enrichment”，没有检查所有玩家是否真正拿到了资料。

触发条件：首次游戏内查询有玩家战绩或段位失败，但仍生成了合法 DTO；之后阵容和 gameflow session 内容保持不变。即使网络恢复，轮询和前端手动刷新也可能只取回同一个缺失快照。

需分别记录“尝试过”“成功”“空记录”“失败”，为失败字段安排重试，并给手动刷新提供真正的 force 语义。

### R3 / P1：旧相遇归档在切号时会丢失其他账号记录

`src/backend.zig:1984` 用当前账号合并整份归档，再写回同一个 `history/encounters` 项。`src/backend/encounters.zig:21` 同时遍历新旧记录，`src/backend/encounters.zig:35` 丢弃非当前 owner 的记录。

已用纯虚构样本复现：A 账号旧记录 + B 账号新记录，合并后只剩 B。读取时按账号隔离是必要的，但不能在保存 B 数据时把 A 的持久记录一起过滤掉。

按用户最新要求，不把修复方案扩展成新的玩家档案系统。如果选择只使用近期战绩，需要退出这一长期归档写入链路；如果选择完全按 Akari 保留小型相遇索引，则按账号分别保存。现有用户数据不应在迁移时被主动删除。

### R4 / P1：相遇详情“有显示”，但加载和交互还未闭环

- 卡片标签：`frontend/src/components/PlayerCard.vue:113` 只拼接次数和时间；点击会触发整个卡片的玩家抽屉，没有 Akari 那样的标签浮层表格。
- 抽屉：`frontend/src/components/PlayerDetailDrawer.vue:163` 已有最近五条标签内记录，下方另有双方英雄/KDA/胜负列表。这部分应复用。
- 十人弹窗：`frontend/src/components/EncounterMatchModal.vue:32` 从相遇行重建参与者摘要，没有装备、符文、伤害、经济等完整战绩字段，也不会自己按游戏 ID 查询详情。
- 本地记录读取：`src/backend.zig:1714` 在 live 模式先查询当前账号、LCU 战绩和 SGP，才返回已有归档。用户展开本地记录也会等待网络。
- 请求竞争：`frontend/src/components/PlayerDetailDrawer.vue:94` 没有请求代次或取消；快速换人时，前一个人的慢响应能覆盖新的列表，失败也被静默变成空列表。
- 抽屉快照：`frontend/src/views/LiveView.vue:188` 保存选中对象，`frontend/src/views/LiveView.vue:375` 一直将它传给抽屉；后续阵容换成新对象时，抽屉顶部信息不会自动改为该玩家的最新资料。

### R5 / P1：结算补全依赖页面查询，不能保证关掉页面后仍然完成

游戏中保存的记录在 `src/backend.zig:4077` 标为 `liveSnapshot`，没有最终 KDA/胜负。完整数据通常由个人历史查询或打开相遇列表后补齐。

`frontend/src/App.vue:80` 在结算阶段只使当前活跃的战绩查询失效；`src/backend.zig:1405` 仅在本人历史查询时持久化相遇战绩。这不能证明仅停留在对局页、切页面、退出应用之后，所有相遇都能完成结算补全。

另外，`src/backend/encounters.zig:21` 总是让 newest 覆盖 existing，没有“已结算优先于未结算”的规则。隔离样本已证明，晚到的未结算行能抹掉已有 KDA/胜负。这是合并函数的确定行为，实际触发频率仍需集成验证。

不保存长期记录的方案也需要结算后刷新内存中的近期战绩，让下一局正确识别“上局队友/对手”；无需因此引入全年持久化。

### R6 / P2：一年限制应取消，不再修成新的保留期规则

现有 `src/backend.zig:1671` 和 `src/backend.zig:1979` 将 `writeIsoTimestamp` 写出的带 JSON 引号字符串直接用于时间比较，而归档中的时间已经解码、不带引号。隔离样本中，2024 年记录没有被 2025 年截止时间排除。

用户已明确不需要一年限制。因此最终动作是移除相遇查询和展示里的年度条件，改用 Akari 的“时间倒序 + 展示数量上限”。旧问题作为代码退役边界记录，不安排新的年度过滤功能。

### R7 / P2：界面有些字段比实际数据能力更完整

`src/backend.zig:4532` 将玩家来源统一标为 `lcu`，`isStale=false`、`error=null`，即使实际使用 SGP、缓存或部分请求失败也是如此。无段位数据还可能显示成“未定级”，与真正未定级混淆。

`src/backend.zig:3000` 将队伍前/中/后期、团战构成固定输出 0，但界面显示量表。`src/backend.zig:5159` 的总评分是近期胜率/KDA 规则分，下一行的分项分数与总分也并不相加一致。应解释为样本指标，不能当成已经验证的真实胜率或阵容模型。

`frontend/src/components/PlayerDetailDrawer.vue:162` 写“近10场”，却统计整个 `recentMatches`，后端已能返回 20 场，需要统一统计窗口和未完成对局处理。

### R8 / P2：一些入口尚未有对应真实能力

`frontend/src/views/SettingsView.vue:296` 有赛前 AI 总结开关及模型配置，但当前命令注册表与服务层未找到实际推理流程。`frontend/src/services/backend.ts:53` 的 replay 使用 fixture 并改 phase/id，也不是上一局真实数据回放。

建议先明确或隐藏未接通入口，避免用户将配置已保存理解为功能已启用。AI 若后续实现，可以使用已有 Native credentials 接口存密钥，不必放进普通配置快照。

## 3. 5 人 / 10 人加载的实际实现

| 路径 | 当前行为 | 证据 |
| --- | --- | --- |
| 界面首屏 | 先请求快速阵容，再启动完整资料查询 | `frontend/src/views/LiveView.vue:25`、`:321` |
| 游戏内 2999 | 双方队伍并行；每队内部逐玩家线程并行 | `src/backend.zig:3933`、`:4293` |
| 选人 / gameflow | 先完整生成我方，再生成敌方；每队内部玩家并行 | `src/backend.zig:5282`、`:5287`、`:5386` |
| 单玩家资料 | 身份解析在前；段位、LCU 战绩、SGP 战绩可并行 | `src/backend.zig:4339`、`:4400` |
| 返回方式 | 所有相关线程 join 后，整批返回 | `src/backend.zig:4308`、`:4425` |
| 查询超时 | 玩家请求配置上限 1800ms；前置请求仍使用普通超时 | `src/backend.zig:1454`、`:4334` |
| 缓存 | 段位 20 秒、战绩 60 秒，另有整局缓存捷径 | `src/backend.zig:1452`、`:714` |
| 全应用命令 | 一个 bridge worker；大部分命令全程持锁 | `src/main.zig:217`、`:255` |

所以“已经改异步”是部分真实，但还不能等同“玩家资料随到随显示，其他功能也不受影响”。

冷缓存时，十人路径可能同时产生约 30 个资料 HTTP 请求，以及等待这些请求的玩家线程、队伍线程。代码没有统一的网络任务并发预算。SGP 和 LCU 同时发起后仍等待二者结束，即使其中一个已经返回足够好的战绩。

注意：1800ms 是传入 WinHTTP 各阶段的超时值，见 `src/lcu/http_windows.zig:44`，不是整个玩家资料任务的严格截止时间，不能据此承诺十人 1.8 秒全部加载完成。

当前耗时近似为：前置请求 + 身份解析 + 本批最慢的资料查询。选人双队路径还会叠加另一队批次的等待。建议的目标是先完成阵容，再逐玩家、逐字段更新，详情和额外样本放到后台。

依据用户对不必存储玩家的偏好，推荐将展示和判定对齐 Akari，优先从已加载近期战绩派生相遇。这样不需要新建长期玩家档案；相应地，超出已获取战绩范围的旧相遇不能保证记住。若选择完全对齐 Akari 的历史记忆，再保留小型相遇索引即可，仍不需要重复归档每局所有玩家的完整数据。
